# Changelog

Notable changes to `@crafter/vcut`. Entries say what changed and, where it is not obvious, what measurement led to it.

## 0.21.0

### Added

- **`vcut rounds <media> --diff N M --verify-delta` names only the spans a round actually changed (#46).** From a real 14-round session's own retro: "most of my token spend from round 6 onward was re-verifying already-clean material." `rounds --diff` already knows what changed between two committed rounds; `--verify-delta` turns that into the master-time spans a downstream agent has to re-hear, plus the immediate neighbours of every new join, since a join is exactly where a duplication or a clipped word appears. The naive version of this is wrong twice over. Diffing master-time positions flags everything after the first cut, because a cut anywhere shifts every later segment. Diffing `segment.id` is worse and less obvious: `build-edl.ts` assigns ids by array index, so one removal renumbers every id after it and an id-based diff reads 22 untouched survivors as changes (measured, rounds 11 to 12 of session `bfd7c6fac64c2968`: 23 of 92 segments flagged, 28% of the render, all false, filed as #53). Identity here is the source-time span itself, `sourceId + inMs + outMs`, which is what `build-edl.ts` already treats as a segment's defining data; a boundary re-clamp changes `inMs`/`outMs` by definition and so falls out of the same check with no separate "moved" category. "Immediate neighbour" is adjacency in the round's own segment sequence, not a duration window, so the feature carries no invented tolerance. Measured against that real session, all 13 adjacent round pairs: **22 of 745 segments flagged, 77.4s of 2930.4s render-equivalent, a ~38x reduction** against re-sweeping the whole render every round. Rounds 8 to 9 flag nothing at all (that round changed no content), and the weakest pair, 4 to 5, still reduces 3.4x.
- **`vcut verify --windows <media> [flags]` turns the hand-run listener-grade window sweep into one call (#45).** A whole-file transcript averages: reading ninety seconds collapses three attempts at the same line into the likeliest single reading, and the same audio cut to sixteen seconds returns what was actually said, the reasoning `rounds-methodology.md`'s own working-a-round section already states for every other short-window instrument in this codebase (`converge`, `say --transcribe`, `peek`, `joins`, `nonspeech --verify`). An agent found this the hard way running the method by hand, serially, one window at a time: ~140 raw tool calls in one round. `verify --windows` tiles the media in `--window`-sized spans (default 16s, the width the hand method used) every `--stride` ms and reports `repeatedPhrases` (a 3-word run one window's own text repeats, merged with two consecutive sentences opening on the same 2 words, the stacked-filler shape a 3-word run alone misses), `truncatedEdges` (a window whose last heard word carries no terminal punctuation), and, with `--transcript`, `anomalies` against a cached whole-file SRT. Unlike every other `trx` caller here, windows transcribe **in parallel** (`--concurrency`, default `min(4, cpus)`): every other command stays sequential because it interleaves with other work sharing one machine, and a window sweep has no other work to interleave with; its windows share no state (a short `ffmpeg` extract plus one `trx transcribe` call touches nothing any other window touches). Measured (2026-08-12, `ps aux` against a live `whisper-cli` process, large-v3-turbo): each concurrent transcription process holds roughly 1.8GB resident, independent of window length, which is why concurrency is a real flag rather than unbounded `Promise.all`. Verified against the real fixture from #45 (`normal-mcp-demo-round12.wav`, 358.5s): a 16s window at 224-240s reports both `repeatedPhrases` entries the issue names, `"reciben un poema"` x2 and `"y bueno"` x2, in one call, and the full sweep surfaces 18 repeated phrases across 7 windows where a human ear had flagged one zone. One correction to the premise this verb was filed under, measured rather than assumed: re-transcribing this particular render end to end **does** carry both defects verbatim, so whole-file smoothing is not what hid them here. What hid them is that nobody transcribed the render at all. The session transcript is of the source in source-time, and neither defect exists there, because the duplication is created by the join between two segments that were never adjacent in the source. No transcript of a source can show a defect its own cut invents. That is the case for this verb, sharpened rather than weakened, and it is filed as #52.

### Fixed

- **A many-segment audio-only render cost minutes because the source was decoded once per segment (#41).** Every segment's `atrim` referenced `[0:a]` directly, and ffmpeg inserts the fan-out itself once per extra consumer of a label, so a 180-segment EDL paid that cost 180 times. Measured on a synthetic 700-second source: decoding the whole audio track once takes 0.66s, while cutting it into 180 segments with no filters at all took 68s. Naming the fan-out with one explicit `asplit` (and `split` on the video path) collapses it to a single decode feeding N windows. End to end through `runRender` on a 700-second source, 490 seconds kept: **293.3s to 43.4s at 180 segments**, 53.4s to 21.0s at 50, 32.7s to 19.8s at 20. **Byte-identical output**, verified as bytes rather than argued: the same EDL rendered before and after hashed to the same sha256 at 1, 5, 20, 50 and 180 segments. `asplit` is what ffmpeg was already inserting, so this only writes down a graph edge that was always there; a source feeding a single branch emits no split and keeps its exact prior graph string.

### Changed

- **The "0.25s against 31.8s" audio-only claim is corrected across the manual, README, website and help text (#41).** That figure was measured on a 54.6-second cut before loudness normalisation entered the graph, and it was being read as "audio-only is instant" at any scale, which is what made per-find commits look free. The real law, measured: cost tracks **the audio the cut keeps**, not the segment count, at roughly **1 second per 14 seconds kept** — 22 and 180 segments over the same 84 seconds of kept audio cost 6.9s and 8.7s, while 490 seconds kept costs ~34s at any segment count. `loudnorm` is ~95% of that, single-threaded and linear in kept audio: it is the floor, and no flag removes it.
- **Commit cadence is now a stated rule with its wall-clock math, in the core skill and the commit section (#41).** Every `commit` re-renders the whole cut, so its cost is set by kept audio rather than by how much changed since the last one. The run this came from paid six commits on a 700-second source at ~9 to 9.5 minutes each, 50+ minutes of foreground ffmpeg, each one re-rendering everything its predecessors had already rendered. The rule: propose every cut the evidence supports, then commit once and verify the batch. It governs how many commits a round costs, never whether a cut gets its second round — the rounds gate is unchanged.

## 0.15.0

### Added

- **`vcut joins --edl <path> --render <path> [--report <path>]` verifies every semantic join in one call (#15).** `edl build` already names what a semantic cut removes (`semanticCuts[].removedText`) and which segment opens right after it (`boundariesAfterSpeech`'s own warning); checking whether the render actually landed clean at that boundary meant `locate` (find the master position) plus `say --transcribe` (hear the window), once per cut. On a real 11.7-minute run (2026-08-10, testing-10m.mp4), verifying 9 joins that way cost ~14 calls, the same session where 3 `removedText` wolves each cost a separate refutation call. `joins` derives each join from the EDL through `boundariesAfterSpeech` directly rather than re-deriving the boundary rule, checks the EDL's own master-time map against the render's measured duration first (`renderCheck`, same shape as `locate --render`), then re-transcribes a window around each join (default 4s, sequentially — one `trx` call at a time, never `Promise.all`, the same reasoning `nonspeech.ts`'s `verifySpansSequentially` and `say --positions --transcribe` already apply) and reports a `reading`: `lands` (the window's carrying words do not majority-overlap the cut's `removedText`), `removed-text-leaked` (they do, majority overlap — the tail of removed speech may have survived), or `check-by-ear` (the window carries too little to judge, the same honest-limits stance `peek`'s `viewsDisagree` already takes). `--report <path>` points at a build report for `removedText`/`reason`/`driftSuspect` per join, defaulting to a sibling `report.json` next to `--edl` (the shape `vcut commit` writes into `rounds/round-N/`); its absence is a supported state and `joins` still runs with those three fields `null`. Verified against the real `testing-10m.mp4` render (`test10-preview-60.mp4`, 176 segments, 9 accepted semantic cuts): `renderCheck.agrees: true` (22ms off a 551.4s render), 8 of the 9 semantic cuts produced a join (the 9th opens the file, which `boundariesAfterSpeech`'s own index-0 rule excludes — nothing precedes it to join to), 7 read `lands` including the sneeze join ("va a ser mucho mejor. Lo que decían es que el...") and the Typefully join ("Está usando Typefully. Puedo aprovechar..."), and one read `removed-text-leaked`. That one call cost ~15s wall time for 8 re-transcribed windows, against ~14 calls by hand for 9. The `removed-text-leaked` join was investigated rather than accepted at face value and turned out to be a false positive: the cut's `removedText` was the speaker stumbling on "agregar verificabilidad" three times before landing it, and the surviving sentence legitimately reused "agregar verificabilidad" as its real content — carrying-word overlap cannot tell a leaked tail from a kept sentence sharing vocabulary with its own discarded false starts by construction. A wider `say --transcribe --window 8` confirmed the join reads clean ("nos basamos mucho en este principio de agregar verificabilidad a los instrumentos de los agentes..."), the exact command `joins` names in that join's own `next`. `removed-text-leaked` and `check-by-ear` are documented as places to look, not verdicts, in the same terms every other disagreement reading in this codebase already uses.
- **`carryingWords` (`peek.ts`) and `probeDurationMs` (`locate.ts`) are exported.** `joins` needed the identical carrying-word comparison `peek`'s `viewsDisagree` already uses and the identical ffprobe duration measurement `locate --render` already uses; both are now shared rather than duplicated a third time.
- **`vcut schema joins`** documents the contract.
- **`vcut open <media>` opens or resumes a content-addressed session.** `~/.vcut/sessions/<sha256-16>/` holds a session keyed by the source's own bytes, not its path: the same content at two paths shares a session, and the same path pointed at new content opens a new one rather than serving stale cache silently. `open` runs `detect` once and caches the report; a second `open` on unchanged media at the same preset reuses it (`cached: true`, and the difference is not subtle — seconds against a fraction of one on a real 11.7-minute recording). A different `--preset` re-detects on purpose. Invalidation is two levels: a cheap size+mtime check against `meta.json`, re-hashing only when that disagrees, and a sha that changes on re-hash is never mixed in silently — a later verb turns it into a clear error naming both hashes and the session the new content belongs to.
- **Refs**: the session's cached silences become `b001`, `b002`, ... — the speech blocks between them, in time order, stable identifiers a later verb can point at instead of a raw millisecond pair. They derive strictly from `detect`'s own silence list, never from `vcut silences` (a different, caller-chosen resolution). A re-open with a different preset bumps the session's `gen` counter, since refs from an earlier gen describe boundaries the session no longer has.
- **`vcut schema open`** documents the contract.
- **`vcut peek <media> (--ref <ref> | --at <sec>) [--window <sec>]`.** The four views of one position, aligned in a single call, with their disagreement named rather than left for an agent to notice across four separate outputs. Resolves the session for `<media>` the way `open` does (creates it if absent, otherwise `checkSession`'s cheap size+mtime path), then reports `transcript` (words the session's cached SRT claims inside the span), `heard` (the span re-transcribed just now through `transcribeWindow`, the instrument that settles a wolf), `blocks` (speech/silence at fine resolution, -33dB/0.08s min, over span ± 1s — the same threshold and minimum the manual already names for placing a boundary around a filler), and `level` (peak/mean dB over the span). `viewsDisagree` compares `transcript` against `heard` on carrying words (4+ letters, the same comparison `converge` already uses for the same reason: short words drift between two transcriptions of the same audio and comparing them reports noise, not disagreement) and names one of `transcript-claims-more`, `heard-more`, `aligned`, or `soft-speech-below-threshold` — the last one firing when the fine-resolution `blocks` read silence for the whole span but `heard` still carries words, which is the "Me siento muy..." class neither `silences` nor `detect` can see because both work from a volume floor a transcriber does not need. On a real 11.7-minute run (2026-08-10, testing-10m.mp4) that motivated this slice, roughly six calls went to nothing but settling exactly this kind of disagreement by hand, one `say --transcribe` per wolf. Verified against the same recording's three known wolves: the "Me siento muy" zone (550.0s, 5s window) read `heard-more` — the whole-file transcript had already recovered the recovery ("Me siento muy feliz") but the short re-transcription window cut off before it; the fused zone (55.5s, 6s window) read `heard-more`, the transcript holding two clamped words against a full recovered sentence; the closing zone (672.5s, 5s window) also read `heard-more`, the short window truncating "cambiado" that a wider window and the whole-file transcript both carry — an honest instance of the manual's own caveat that a short-window transcription is noisy and a disagreement is a place to look, not a verdict.
- **`vcut schema peek`** documents the contract.
- **`vcut cut <media> --refs <ref[..ref]> --kind <kind> --reason "<text>"` proposes a semantic cut against a session, and shows what it removes before any build runs.** `--refs` resolves a single block ref or an inclusive range (`b042..b044`, from the first ref's own start to the second's own end) through `peek`'s own `resolveRef`, so an unknown ref or one from a stale generation is the same usage error `peek` already gives, naming the ref and the session's current `gen`. `--span <startS>..<endS>` is the escape hatch for a raw span when no ref fits, mutually exclusive with `--refs`. This is the corrective the arc's shaping doc names directly: a measured block mis-assigned to the wrong words — the class of mistake that removed "todos estamos" instead of "en nuestra propia" on a real recording, invisible until a render — cannot be written here, because the span comes from a ref pointing at a block the session already measured. `removedText` is quoted from the session's own cached transcript at propose time, not re-transcribed, and the session must already exist: `cut` never creates one, unlike `open` and `peek`. `--list` prints the session's accumulated proposals with their `removedText`; `--drop <index>` removes one by 0-based index, so a human changing their mind is a normal step rather than hand-editing `proposals.json`. Verified against testing-10m.mp4 (11.7 minutes): a range covering the recording's sneeze zone echoed back "estornudar. ¡Wow! Ah, perdón, estorné. Eso sí, borra la profa." exactly as spoken, reading the sneeze and the speaker's own spoken instruction to cut it before any build ran.
- **`vcut commit <media> --output <path> --campaign <id> [flags]` builds and renders a session's accumulated proposals in one call.** The build calls the same seam `vcut edl build` uses internally (`runBuild`, extracted from `build-edl.ts` with the same minimal-refactor discipline B-V1 applied to `detect.ts`), so `commit`'s draft EDL is byte-identical to running `edl build --detect <cached> --semantic <path>` by hand on equivalent inputs — pinned by a test that runs both paths against the same detect report and proposals and diffs the result. The EDL writes to the current directory by default (`./edl.json`), never only inside the session, matching the shape's B6 note that commit produces the same draft EDL the standalone pipeline produces and the approval gate stays untouched. Rendering defaults to `--audio-only` (a `.wav` beside the EDL), matching the manual's own per-round rule; `--video` renders the preview instead. **Master mode never happens here** — approval is a human edit to the EDL followed by the existing `vcut render --edl <path> --mode master`, and `commit`'s help and the manual both say so. Records the round in the session (`rounds/round-N/`: the EDL copy and the build report); renders and wavs stay out, matching everything else the session already holds. A real bug surfaced building this against a session with a cached transcript: the session's own detect report carries whatever transcript path the original `open --transcript` call was given, which can differ from the session's own copy at `cachedTranscriptPath` — `commit` now points the report at the session's copy before building, the same thing `peek` already does, rather than trusting a path that can move or vanish. Verified against testing-10m.mp4: committing two proposals (a sneeze zone by refs, a pre-roll by `--span`) produced a 14.2% removal with both `removedText` fields populated and an audio-only render whose sneeze-zone cut boundary landed within 8ms of a hand-built EDL cut over the same zone.
- **`vcut schema cut`, `vcut schema commit`** document the contracts.
- **`--fields <a.b,c,d>` projects JSON output to only the requested dot paths.** A real 11.7-minute run made roughly 40 `python3 -c` calls, each extracting 2-3 fields from a full payload it had already read, with `jq` on `PATH` the whole time — an external post-processor is a second syntax to recompose per call, a native flag is part of the output contract, discoverable in `--help` and `schema`. `--fields removalPercent,semanticCuts.removedText` implies `--json` (asking for fields is asking to parse) and keys each result by the exact path requested, so the shape returned matches the flag written rather than a reconstructed nested object. An array segment projects the rest of the path over every element: `semanticCuts.removedText` over nine cuts returns the array of nine strings. A path that does not resolve lands in a `fieldErrors` entry naming it rather than failing the whole call — an agent asking for a field that moved should learn that, not lose the call. `vcutVersion` always rides along regardless of selection, since it is the version stamp and not a field a caller could ask away. Implemented once in `emitJson` (reading `process.argv` directly, the same precedent `packageVersion` already set reading `package.json` unprompted) rather than per command, so every one of the ~30 call sites across every command gets it for free. Documented in the core skill's Output contract section alongside `--human` and full JSON as the same three-tier idea at three resolutions — never three different truths about one run.
- **`edl build`'s `semanticCuts` entries gain `driftSuspect: true` when `removedText` sits on drifted cues.** `removedText` inherits transcript drift the same way the whole-file transcript does: on a recording with 326 drifted cues (`detect`'s own drift warning), `removedText` cried wolf three times in one run — claimed removed text that survives, or the reverse — and each wolf cost a `say --transcribe` to refute before the real cause turned out to be drift rather than a bad proposal. `edl build` now reuses `detect.ts`'s own `wordsContradictingSilence` check, scoped to the words a span's `removedText` actually draws from, rather than a second implementation of that comparison, and marks the cut `driftSuspect: true` with a matching warning when any of them contradict measured silence. Present and `true` only on a suspect span, absent (not `false`) on a clean one. Verified against a real 700.8s recording's `detect.json`/`proposals-final.json` (2026-08-10, testing-10m.mp4): all 9 accepted semantic cuts came back `driftSuspect`, including the three known wolves this issue named (the 579.04-580.38s "Ninguna" span, the 165.28-172.02s span, the 662.35-671.83s closing span) — the recording has 326 of 1842 words (17.7%) flagged by `detect`'s own drift check, spread across the full 700s, so a span of any real length is statistically near-certain to contain at least one. That saturation is `detect`'s own "no invented tolerance" rule (the drift warning has never filtered on how far a word drifts) applied at span granularity rather than a defect in the derivation, and is reported honestly rather than tuned against with an invented threshold the issue gave no authority for. Deliberately not a re-transcription: the windowed-retranscription alternative the issue also named answers a harder question `peek` and `say --transcribe` already provide on demand, and running one automatically per span would spend a transcription call whether the span needed it or not.
- **Advisory lock on session writes (B-V4, B7-Q1).** `cut`'s mutating paths (propose, `--drop`) and `commit` take the session's lock (`lock.json`: `{pid, startedAt, verb}`) before writing and release it in a `finally`; `--list` and every reader (`open`, `peek`, `rounds`) never lock. A second writer finding a live pid's lock gets `SessionLockedError` naming that pid, its verb, and how long ago it started, rather than a race on `proposals.json` or `rounds/`. A lock whose pid is no longer alive is stale and clears itself automatically on the next attempt by anyone — nobody has to notice and delete `lock.json` by hand. Verified against the real `testing-10m.mp4` session: writing a `lock.json` naming this shell's own live pid and attempting `cut` refused with that exact pid, verb, and age; writing one naming an out-of-range pid (`999999`, `process.kill(pid, 0)` reports ESRCH on it) and attempting `cut` cleared it and succeeded, with no `lock.json` left behind afterward. Not a kernel-level lock: two writers racing the same instant could both pass the check before either writes the file, which is honest about the courtesy this is between cooperating writers rather than a guarantee against an adversarial one.
- **`vcut session list|gc [--apply] [--older-than <days>]` (B-V4, B7-Q2).** `list` reports every session under `~/.vcut/sessions/`: source path and whether it still exists, size on disk, creation time, committed round count, and lock state. `gc` classifies every session against `orphan` (source gone), `committed` (at least one successful `commit` ran — a successful commit now calls `markCommitted`, writing a `committed-at` marker, since nothing marked a session disposable before this), `older-than` (only with `--older-than <days>`; omitted, age alone never qualifies a session — no invented default), and `locked-protected` (a live process holds the lock right now, which always wins and is never deletable regardless of any other reason). Dry-run by default; nothing is deleted until `--apply` is also passed. The EDL a human approved is never at risk: `commit` writes it to `--output`/`--edl`, never inside a session directory this command manages, so clearing a whole session can only ever remove the disposable detect cache, transcript copy, refs, proposals, and round history behind it. Verified against the real `testing-10m.mp4` session (2 committed rounds, predates this marker so `committedAt: null`): `gc` dry-run classified it with zero reasons (source exists, no age filter given, not locked) and `deletable: false`, deleting nothing.
- **`vcut doctor` reports sessions.** One line in human mode, a `sessions` object in JSON: count, total size in MB, orphan count (source file gone), and the oldest session's creation date. Absent sessions directory reports zero across the board rather than an error — a machine that has never run `vcut open` has nothing wrong with it. This is the detector class that was missing when a different cache directory (`~/.kai/logs`) grew to 609MB unnoticed: a cache that grows has no watcher unless something is built to watch it. Verified against the real session store: `1, 0.25MB, 0 orphan(s), oldest 2026-08-11T00:34:21.264Z`, matching `du -sh` on the session directory exactly (258871 bytes).
- **`vcut rounds <media> [--diff [N M]]` (B-V4).** Without `--diff`, lists every round number a session has committed, ascending. With `--diff`, compares round `N`'s build report against round `M`'s (defaulting to the latest two when both are omitted): `removalPercentDelta`, `segmentCountDelta`, and `semanticCuts` matched between rounds **by span overlap** rather than array position, so a proposal whose exact edges shifted slightly between rounds (absorbed into a wider merged cut, re-clamped) still reads as the same cut rather than one removed and one added — reported `added`/`removed`/`changed`/`unchanged`. This diffs what each round's build asked for (the `BuildSummary` `commit` already writes to `rounds/round-N/report.json`), not what either round's render actually says: a text-level diff needs a transcript of each render, and a session never stores renders or their transcripts (B2-Q2: cheap to regenerate, expensive to keep), which the command's own help says rather than implying coverage it does not have. Verified against the real `testing-10m.mp4` session's 2 rounds: `-2.07%` removalPercent, `+2` segments, and both semantic cuts correctly read `changed` (round 1's cuts carried no transcript text; round 2's, built after a transcript was cached, carried the full quoted text of the sneeze zone and the pre-roll).

### Fixed

- **`open`'s `gen` bumped on every preset transition, including returning to a preset the session had already used.** Reproduced against the real CLI before this fix: `open` (default `noisy`, gen 1) → `open --preset clean` (gen 2) → `open` (default `noisy` again, gen **3**) — even though the third open's blocks were byte-identical to the first's (same source, same threshold, same silences), and a caller holding a `b`-ref from the first open saw it rejected by name on the third despite nothing about the recording having changed. `refs.json` now carries `presetGens`, a map from every preset a session has ever detected with to the gen it was first assigned; `writeRefs` derives `gen` from that map rather than from whether the immediately previous write's preset differed, so `noisy` → `clean` → `noisy` now reads gen 1, 2, **1**, never 1, 2, 3. `readRefs` backfills `presetGens` for a `refs.json` written before this fix (the only preset on record is the current one, at the current gen — exactly what a single-write history implies), verified by loading the real pre-B-V4 `testing-10m.mp4` session (`gen: 3, preset: clean`, no `presetGens` field) and confirming it backfills to `{clean: 3}` and stays there on a same-preset re-open.
- **`commit` patched a session's cached `transcript.path` on every call instead of once, at cache time.** `open --transcript` caches a copy of the SRT into the session, but the detect report's own `transcript.path` field still carried whatever external path the original call was given — a path that can move or vanish after `open` returns. `commit` compared it against `cachedTranscriptPath` and rewrote a local copy on every single call to work around it; `peek`/`cut` already sidestepped the whole problem by reading straight from `cachedTranscriptPath` rather than trusting the field at all. `open` now points the cached detect report's `transcript.path` at the session's own copy once, right after caching (`pointCachedTranscriptAtSession`, `session.ts`), so every later reader of `cachedDetect` gets a path guaranteed to still resolve. `commit` calls the same helper only in its fallback path (recovering a cache file that went missing underneath an otherwise-normal session, where no `open` ran to have fixed it already) instead of re-deriving the fix inline.
- **`markSemanticRisk` compared segment edges against a proposal's raw span instead of the span it merges into.** A proposal that sits close enough to a neighbouring silence cut (or another proposal) absorbs into a wider cut before segments are inverted — the same merge/absorb step `removedText` and `boundariesInSilence` already read from. A ~9.4s proposal that absorbed into a ~10s merged span used to be compared against its own raw 9.4s edges, so segments touching the merged span's real, wider boundary read `semanticRisk: 'none'` — exactly the segments a reviewer approving "what did the model choose to remove" needs flagged, since the render carries the full merged cut regardless of which raw proposal edge produced it. `markSemanticRisk` now resolves each proposal through `clampedSpanFor` (the same function `describeSemanticCuts` already uses) before comparing edges. Deliberately not `cuts.filter(reason === 'semantic')` on the merged list: a merged interval reports `reason: 'silence'` the moment it absorbs even one differently-typed cut (`mergeIntervals`'s own rule), so that would have dropped exactly the absorbed spans this fix exists to catch.

### Changed

- **`say.ts`'s `measureLevel` is exported.** `peek` needed the identical ffmpeg-plus-volumedetect measurement `say --transcribe` already had; exporting it kept `nonspeech.ts`'s own copy from becoming a third one written for `peek` specifically. `nonspeech.ts`'s copy is unchanged and is now the only remaining duplicate.
- **`build-edl.ts` exports `runBuild`, a callable seam for everything `buildEdlCommand` does once a detect report and proposals are in hand, minus reading either off disk and minus printing.** `buildEdlCommand` itself now calls straight through it, so its behaviour and every existing test are unchanged; `commit` is the first caller that needed it as a function rather than a CLI invocation.
- **`render-edl.ts` exports `runRender`, the same kind of seam for `renderCommand`.** `commit`'s audio-only render step calls it directly on an in-memory EDL rather than round-tripping through a temp file or shelling out to vcut's own CLI from inside vcut, which the shaping doc ruled out explicitly.
- **`build-edl.ts` exports `BuildSummary`.** `rounds` needs to type the build reports it reads back from `rounds/round-N/report.json`; it was previously module-private since nothing outside `build-edl.ts` read one as a typed value before this slice.

### Docs

- **`converge`'s two contract assumptions are documented in the core skill and the debug skill (#18).** It stops at the first window lacking the phrase, which is only the right boundary when the retake is contiguous and the transcriber is stable. On real stumbled speech (2026-08-10), probing from outside the recurring wording returned an immediate false clear through discard babble (`boundaryMs: 84500`, useless), and a single flaky short-window transcription dropped the phrase for one window and triggered an early first-clear while the phrase still recurred nine seconds later. ### Fixed (#14, cherry-picked from hotfix-issue-14 at 44704ce)

- **`edl build` no longer clamps the last kept segment to the container's duration.** A real 11.7-minute screen recording (`testing-10m.mp4`, 700.8s by `ffprobe format.duration`) has a video stream that ends at 700.717s, 83ms short: the audio device kept the microphone open a beat after the capture stopped drawing frames, which is normal for a screen recorder and not for a camera. `probeSource` read only `format.duration`, the longest of the container's streams, so the source's `durationMs` and the final segment's `outMs` both claimed 700.8s of video that did not exist. `render`'s video trim asked ffmpeg for those 83ms and got them clamped away silently rather than as an error, so the render came out short and failed its own frame-count and duration checks (issue #14). `probeSource` now also reads each stream's own `duration` and exposes `videoDurationMs`; both the EDL's `Source.durationMs` and `invertToSegments`'s clamp use it instead of the container figure. Reproduced on a synthetic fixture built with the same shape (`testsrc2` video ending at 5.000s, `sine` audio running to 5.084s): the last of 15 segments used to claim `outMs: 5084` and now claims `5000`, and the render that used to fail `render frame count differs from EDL duration` now passes.
- **The frame count and duration checks report the numbers, not just their names.** `render frame count differs from EDL duration` and `render duration differs from EDL` gave no way to tell a one-frame miss from a broken render without re-deriving the EDL's own arithmetic by hand. ### Fixed (#20)

- **A many-segment, fps-converting render no longer fails its own frame-count and duration checks.** `fps=` ran inside every segment's own filter chain, before `concat`, against that segment's PTS-reset clock — `round=near`'s documented default (`ffmpeg -h filter=fps`) applied independently per segment rather than once to the assembled timeline. On the real 176-segment, 60fps-source-to-30fps-output EDL #14 surfaced this against: `expected 16542 frames, got 16588` (+46), `expected 551406ms, got 552933ms` (+1527ms). Isolated on a synthetic 20-segment fixture (60fps `testsrc2`, irregular segment lengths, no shared edges — the shape real silence-detected cuts actually produce): 5 of 10 segments in the hotfix's own isolation, +16 frames at 20 segments and +51 at 176 in this fix's own fixture, scaling with segment count rather than a fixed residue.

  Two changes land together, both scoped to only the render whose output fps differs from a source's own recorded rate (`convertsFps`, keyed off `Source.averageFrameRate`, an EDL field written since 0.14.0 — an EDL with no such field, or one where every source already plays at the output rate, is indistinguishable from native here and keeps the untouched graph and untouched validator arithmetic; every EDL already on disk defaults to that path):

  1. **`concat` now runs once for video and once for audio, instead of one combined call.** ffmpeg's own concat filter manpage documents that a combined call "will use the duration of the longest stream in each segment... and pad shorter audio streams with silence" — and a segment's video trim (quantised to the nearest 60fps frame) and its audio trim (millisecond-precise) almost never agree on duration. That per-segment padding nudged every later segment's start off the source's own frame grid before `fps=` ever saw it. Splitting the two into their own `concat` calls removes the cross-talk; `fps=` then runs once, on `[vcat]`, after concat, against a video PTS clock nothing but `trim` has touched. Measured exact (0-frame delta) at 5/20/60/176 segments both directions (60→30 and the upsampling 30→60 case, checked so this fix does not newly break it) on synthetic fixtures built with contiguous segments (no material cut between them, sharing exact edges).

  2. **The frame-count and duration expectations `outputErrors` checks a render against are derived from the source's own discrete frame grid, not a plain millisecond sum, once fps is converting.** Every fixture above shares edges between segments, which is not what a real detect/semantic-cut EDL looks like: real segments are separated by a gap at nearly every joint (`invertToSegments`'s own output). Re-measuring on a gapped synthetic fixture (irregular segment lengths, cut apart by real gaps, matching `invertToSegments`'s actual shape) surfaced a second, smaller defect the contiguous fixtures could not: ffmpeg's `trim` filter does not round a segment's edges to the nearest source frame, it keeps every frame with `start <= PTS < end` (`ffmpeg -h filter=trim`) — start rounded up to the next frame, end rounded down, exclusive, never nearest. A segment cut off the frame grid always keeps at least as much picture as its millisecond span asked for, never less, and a many-segment EDL compounds that one-sided bias. Rebuilding the real 176-segment EDL and rendering it with fix (1) alone still failed: `expected 16542 frames, got 16547` (+5), `expected 551406ms, got 551566ms` (+160ms) — the segment sum asks for 551406ms, but the source's own 60fps grid can only deliver 551566.667ms of it once each segment's trim-adjusted edges are accounted for. `expectedFramesForConcat` now sums each segment's own frame count in that half-open-interval semantics (`ceil(end*sourceFps) - ceil(start*sourceFps)`), scales by `outputFps/sourceFps`, and rounds once — the same `round(near)` arithmetic the `fps=` filter itself applies to the concatenated clock. Re-rendered the same real EDL after this: `551566016` ms measured, `16547` frames measured, both matching the corrected derivation exactly, validator green.

  Deliberately not applied to native-rate renders: the same ceil-based arithmetic disagrees with the plain millisecond sum on roughly a quarter of single-segment cases and by 1-2 frames on many-segment gapped ones at native rate too (measured on the same fixtures), small enough that the existing 1-frame tolerance has always absorbed it there — changing what an already-passing native-rate EDL is checked against is a second, unbudgeted fix this issue did not ask for, filed as a follow-up below instead.

  Native-rate renders are unaffected: `buildFfmpegArgs`'s graph shape and every filter string are byte-for-byte the same as before this fix when `convertsFps` reads false, confirmed by sha256 on a synthetic native-rate render both with and without `Source.averageFrameRate` present (`3ba77069d56900c779677e1c453a1c8ef88a9f6ae1c543cb2c5df0aec5799aae` before and after).

### Found, not fixed here

- **The frame-count and duration validator has the same discrete-frame-grid bias at native rate, on gapped segments, currently absorbed by the 1-frame tolerance but not always.** Measured on a synthetic 20-segment native-rate (60fps) fixture with real gaps between segments: `expected 879 frames, got 883` (+4), `expected 14647ms, got 14717ms` (+70ms) — both outside tolerance, reproduced identically on the pre-#20 code, so this is not something this fix introduced. A 5-segment version stayed inside tolerance (+1 frame); a 60-segment version failed the same way (+11 frames). The fix above intentionally does not touch the native-rate formula (see the "Deliberately not applied" note): scoping a second correction to the render where it was not measured to be needed was more change than this issue's budget carried. Needs its own issue: the same ceil-based derivation this fix already built, applied to the native-rate path once someone confirms it does not flip an EDL that currently passes.

### Added

- **`vcut nonspeech <render> [--verify]`.** The classifier that finds breaths and mic bumps used to be a bare script (`skills/core/scripts/non-speech.py`), invoked with raw `python3` and closed by reading the whole-file transcript with `vcut say` — which is circular for this class of sound, since that transcript is exactly the instrument that could not see it. Verified against a 21-proposal semantic pass on a 7.5-minute recording: every `removedText` read as the filler or retake its `reason` described, and the warning fired on the two proposals that had merged into one wider cut, correctly naming the drift between the fused span's text and either original reason.

## 0.4.0

Everything here came out of one editing session that took 28 minutes to cut 90 seconds of
video, and out of measuring where that time went. The answer was not compute: it was that
several questions an editor asks constantly had no command to ask them with, so each one was
answered by hand with ffmpeg and arithmetic, and two of those hand-rolled answers were wrong.

### Added

- **`vcut locate`** translates between a position in the master and the source it came from, in either direction. Deriving that mapping by hand is the trap it replaces: accumulating `outMs - inMs` produces a total that can match the rendered file to the millisecond while individual positions land seconds away, with nothing in the agreement to warn you. `--explain` reports the neighbourhood a position sits in; `--render <path>` measures the file rather than trusting the EDL, which records intent. Asking about material that was cut reports it as removed with the next surviving segment, rather than failing.
- **`vcut audit`** compares a render's audio against the source span the EDL points at, segment by segment. Every check the renderer runs on itself is an aggregate, so a render whose segments carried the wrong material passes all of them. It reports rather than fails and stays out of `render`: envelope correlation is weak over short and quiet windows, and a threshold built on it would block good renders. Measured on one 22-segment render: 1.5s to check, 21 segments above 0.85, and the one below was verified by transcription to hold the right words.
- **`vcut say`** reads back what is spoken at a position, with the level there and, with `--edl`, which segment it falls in. It reads an existing transcript rather than re-transcribing a slice, which removes a trap instead of warning about it: a window under about two seconds transcribes as noise whatever it contains, so a gibberish result cannot tell a real word from a model's guess. vcut still never calls a model.
- **`vcut render --audio-only`** renders the audio alone, for the rounds where every question is about sound. Measured on one 22-segment EDL: **0.25s against 31.8s** for the same cuts. The audio graph is unchanged, edge fades and loudness included, so what you hear is what the finished render will sound like: -16.4 LUFS on both paths. Writes lossless audio, because a codec artifact heard while iterating reads as a defect in the cut. Refused in master mode. The result runs a few tens of milliseconds short of the segment sum (31ms on a 54.6s cut), which is `loudnorm` latency draining trailing decay rather than missing material. (0.4.1 corrects this: the shortfall was the time trim cutting against loudnorm's rewritten clock, not latency, and it is gone.)
- **`vcut skills get debug`** documents how to investigate a cut that came out wrong: the question, the method, and the trap that makes the obvious method produce a confident wrong answer. Two of its entries were rediscovered while building the commands that replace them.

### Changed

- **`edl build` warns when a segment opens right after a semantic cut.** That is where the tail of removed speech leaks into a render, and it does not arrive looking like a defect: it arrives as a plausible sentence with the wrong meaning. The condition is the kind of cut, not a distance. Keying it on "the removed span contained words" was the first attempt and it fired on 23 of 24 boundaries, because with word clamping every silence cut brushes the margin around a word.
- **`detect` warns when a word timestamp contradicts measured energy.** Cues drift toward silence, so clamping can hold a boundary open around a pause the detector correctly found. The symptom reads as a threshold problem and the reflex is to change the preset, which does not move it. There is no filter on the warning: measured on one recording the drift ran from 1318ms down to a median of 246ms with no gap to cut at, so it names the worst case with its position instead of inventing a threshold.
- **`detect --human` says whether word clamping engaged**, and with how many words. Running with and without `--transcript` used to print the same summary while producing different cuts: 22.74% removed against 19.55% on the same recording.
- **The manual no longer claims `trx --words` is equivalent to a prompted `whisper-cli`.** It is not: without a prompt the transcript comes back cleaned and the hesitations the manual tells you to keep never reach it. It now points at `trx --preset verbatim`.
- **The loop in the manual carries its commands**, including running `semantic review` every round rather than at the end. It measures the render instead of the plan, which is the only way a pause that survived the cut becomes visible.

### Removed

- **`noiseReduction` is gone from the EDL schema.** Measured on one recording, the background floor already sat at -54 dB and a denoiser at a default setting pushed a weak syllable from -45 dB to -57, which is the same defect as a threshold set too high. There is no safe default because the right amount depends on the room, and unlike a cut it cannot be undone by editing the EDL.

### Fixed

- Cuts separated by a remainder too short to hold a word are merged. Two cuts with 216ms between them do not read as two cuts: the ear hears one broken passage, and a listener flagged exactly that before any metric showed it. Six such islands became zero on the test material.
- `detect` reported filler candidates past the end of the source when the transcript outlived the cut it was made from.
- The renderer's audio contract asked the segment's own source for sound, which fails for a video recorded mute; `audioTrackPolicy` had the same shape of bug, resolving to `explicit-silence` because the picture carried no audio.
- `renderedGaps` promised an empty list when it could not measure but threw if ffmpeg was absent from PATH.

## 0.2.0

### Removed

- **Breaking: `detect` no longer looks for filler words.** The `fillers` field, `--no-fillers`, and the three-language validation of `--lang` are gone. The list held six tokens per language; measured on one Spanish recording it caught 3 spans while the finished cut still carried 19 fillers in 332 words. What it missed were ordinary words that carry no meaning in one sentence and plenty in the next, which no list can distinguish. Filler words are now proposed by a model through `vcut semantic`.
- `--lang` survives as a free-form string, passed through to the semantic export so a model knows what it is reading.

## 0.1.1

### Added

- **`vcut semantic`**: `export` hands the transcript to a model as numbered lines, `check` validates the proposals it returns. vcut never calls a model itself, which keeps it dependency-free and its output reproducible.

### Fixed

- The renderer normalised sample rate but not channels, so a mono source produced a master its own validator rejected. Only visible with a mono source, which is how a separate microphone usually records.
- Word-level transcripts lost the leading space that marks where a word begins, making `"Cra"` + `"fter"` impossible to rebuild.
